### 4. Preprocess artifact cache 失效机制（P0.1 调试期间发现的真 bug）

**现象**：跑 Q1/Q2/Q3 回归时，用户重新上传 `reinforce_vs_A2C_remux.mp4`（之前旧版 pipeline 已处理过），upload endpoint 命中 `.done` 标记 → **完全跳过 preprocess** → 新 ASR/slide stage 永远没跑 → Q2 找不到 REINFORCE → orchestrator tool loop → 400 / "I tried several tool calls" 兜底。表现得像 Q2 代码 bug，实际是 cache hit 屏蔽。

**根因**：[app/main.py:136-142](../app/main.py#L136-L142) `get_video_status(video_id) == "done"` 的判定**只看 `.done` 文件存在性**，不看 cache 里 artifact 是否对得上当前 pipeline schema。pipeline 每加一个新 stage（Phase A 加 ASR、Phase D 加 slide），旧用户视频的 cache 都会变成"假完成"——`.done` 在但缺新 artifact。

**`AGENT_CODE_VERSION` 不管这事**：它只控 prediction_cache（评测预测结果），不控 preprocess artifact cache。两个 cache 域之间没有版本联动。

**修复方向（择一）**：

- **方案 A — pipeline 版本号写进 meta**：[app/preprocess.py](../app/preprocess.py) `preprocess_video()` 完工时把 `pipeline_version = "v17"`（或一个独立的 `PREPROCESS_PIPELINE_VERSION` 常量）写进 meta.json。`get_video_status` 升级为：`.done` 存在 + `meta["pipeline_version"]` ≥ 当前版本 → done；否则 → absent（触发重处理）。**优点**：自动失效，用户无感。**缺点**：每次加 stage 都要记得 bump 这个版本号；旧视频被静默重算可能占很久。

- **方案 B — 用户可见的"reprocess"按钮**：前端 session 列表里每个视频加 reprocess action，调用 `DELETE /api/videos/{id}/cache` 端点。**优点**：明确用户意图，不会意外重算。**缺点**：用户得知道何时该点。

- **方案 C — 关键 artifact 存在性检查**：`get_video_status` 升级为：`.done` + `meta["has_transcript"]` + `meta["has_slides"]` 三者齐全才 done。**优点**：不需要版本号管理。**缺点**：每加新 artifact 都要改这个 check；早期视频可能因 ASR/OCR 失败永远 `has_transcript=false`，被反复重处理。

**建议**：方案 A 最干净，且只需 cache.py + preprocess.py 各改几行。`PREPROCESS_PIPELINE_VERSION` 直接复用 `AGENT_CODE_VERSION` 字符串也行，因为 prediction_cache 失效和 preprocess 失效语义一致（都是"pipeline 行为变了，旧产物不再可信"）。

- [ ] [app/preprocess.py](../app/preprocess.py) `preprocess_video()` 保存 meta 前写入 `meta["pipeline_version"] = AGENT_CODE_VERSION`（或新常量）
- [ ] [app/cache.py:41](../app/cache.py#L41) `get_video_status` 加 schema 版本检查
- [ ] 临时迁移：扫一遍 [data/cache/](../data/cache/)，对 `meta.json` 缺 `pipeline_version` 的，要么删 `.done` 让用户重传时重处理，要么写个一次性 backfill 脚本
- [ ] 不 bump `AGENT_CODE_VERSION`（这是 cache 失效机制本身的修复，不改预测行为）

**临时绕过（已用过）**：手动 `rm -rf data/cache/{video_id}` 强制重处理。今日 27 号已经对 `fb91030524f26c65` 这样做过。
